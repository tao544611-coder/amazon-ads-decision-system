## 二、关键发现（需要在审核时重点决策）

### F1 · 方法论的权威源不是 Notion，而是 box 文件 ⚠️ 最重要

方法论文档自述：**「权威：本 box 文件」**——`/workspace/rubick-ai-org/reviews/广告投放分析方法论_规则_2026-10-26.md`（运营数据分析大佬维护；改规则 = 改 box → Rubick 同步 Notion 原页）。而 PRD 写的是「第一阶段优先继承现有 **Notion** 权威方法论」。

**需要拍板**：系统内方法论（`methodology/*.yaml`）的权威链怎么定？
- 方案 A（推荐）：系统 YAML 自治——Notion/box 是业务权威，系统每次导入方法论改动时生成新版本，导入记录注明来源（box 或 Notion 同步页）+ 人工审核发布。系统不实时追 box，避免静默漂移；
- 方案 B：以 Notion 同步页为准定期重提（但 Notion 是副本，存在同步延迟风险）。

### F2 · 站点与币种：全文金额均为 GBP（UK）

上下沿 £0.10–£2.00、零转化雷达 spend ≥ £2、进单门槛 ≥ £5.00 均为英镑口径（文档明言「不适用 USD 文档默认 max≈5」，且有「UK/昕信适配」表述）。PRD 未写明 6978/6979 站点。**需确认：首期 SKU 6978 / 6979 = UK 站？** 若是，参数原样可用；若含其他站点，参数需按站点分组扩展。

### F3 · 方法论的适用范围比 PRD 首期范围宽

方法论覆盖「Gordon 四位 SKU」并大量引用白名单分组（6384 / 6978_6979 等）、店级锚（昕信全店）。PRD 首期只验证 6978/6979。**不冲突但需注意**：系统按方法论实现规则时，参数（如目标 ACOS 25%）是店级默认 + SKU 例外结构；6978/6979 的例外值（如「6979 深灰暂不停」）应进**产品档案**（PRD 4.2 B 经营目标 / F 特殊规则），而不是写死在方法论 YAML。v1-draft 已按此处理（`target_acos.exceptions` 仅作示例引用，正式版可把 SKU 级例外迁往产品档案）。

### F4 · 方法论依赖的外部资产清单（系统落地映射见 YAML `asset_mapping`）

- `products.md` 白名单分组 → 产品档案
- box 事实表 `reviews/ads-weekly-audit/facts/*.md` → 系统事实层（HR-19 已吸收「先事实后判断」）
- 行动台账 → Action/Observation/Evaluation
- 领星 MCP 取数 → 外部数据源适配器（对应 D11）
- `apollo-ai-bid-skill` 算价脚本 → 阶段一不接入（HR-17 保留边界）

**需确认**：这些 box 侧资产（白名单分组、历史事实表、行动台账）是否有必要在阶段一导入系统作为初始数据？特别是 6978/6979 的历史事实表（W43/W44 周检数据）可直接作为 T1–T3 测试的真实样本。

### F5 · 已知不一致（原文自带，非提取误差）

- `ads-bid-scripts MIN_CLICKS_30D = 30` 与方法论的 20 不一致（原文注明「另案改」）——系统以方法论的 **20** 为准，已记入 `known_inconsistencies`。
- 方法论的「验证窗（多为 7 天或下期周检）」与 §2.4 满窗要求叠加后，实际最短验收周期 = max(7 天, 归因满窗)。系统观察窗口计算应取两者较大值——**这一合成规则是提取推断，原文未明说，审核时确认**。

## 三、提取时的归类判断（审核重点看这些）

以下条目在「程序硬规则 vs 运营知识」的边界上需要人确认归类是否恰当：

| 条目 | 草案归类 | 边界说明 |
|---|---|---|
| HR-11 结构问题优先 | 硬规则（validator） | 「好线顶预算+差线仍烧」可程序检测（OUT_OF_BUDGET 状态 + ACOS 对比），故归硬规则；但「结构未解」的判定细节（什么算解决）偏判断，程序只能拦「结构问题存在时」的 bid 建议 |
| HR-14 事实/推断/待验证三分 | 硬规则（validator） | 程序只能强制建议 JSON 里三个字段分层存在；内容真伪仍靠 AI + 人工 |
| HR-16 bid 口径块完整性 | 硬规则（validator） | 纯完整性检查，可程序化 |
| K-05 恒等式 | 运营知识 | 原文明确「解释口径，非自动执行」——系统不得用它自动算出价并标「可执行」，只能作为 AI 解释与 sanity check 的参考 |
| K-08 归因拆解铁律 | 运营知识 | 「必须显式对比 CPC/CVR/ASP」在系统里落为：分析上下文包自动附带这三个中间量 + 建议模板强制归因段；但「指出底层驱动」是 AI 判断 |
