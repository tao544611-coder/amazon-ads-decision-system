## 1. 总体架构设计

### 1.1 分层架构

遵循 PRD 3.1 四层架构，落地为「一个 Python 包 + 三种接入适配」：

```
┌───────────────────────────────────────────────────────────────┐
│  Agent 接入层（薄适配，可替换）                                  │
│                                                                │
│  ① CLI（typer，人与脚本共用的第一入口）                          │
│  ② DeepSeek Harness 插件（阶段一：调用 CLI/JSON 接口）           │
│  ③ MCP Server（阶段五：fastmcp 包装同一 service 层）             │
└──────────────────────────┬────────────────────────────────────┘
                           │ 唯一通道：ads_core service 层（稳定 API）
┌──────────────────────────▼────────────────────────────────────┐
│  核心业务引擎 ads_core（纯 Python，无 LLM 依赖，可独立测试）      │
│                                                                │
│  ingest ──► quality(文件级) ──► adapters(源适配器×N)             │
│              ──► canonical(统一层+跨源质检+冲突标记) ──► facts   │
│    │                                        │                   │
│    ▼                                        ▼                   │
│  profile(档案)  events(事件)  methodology(方法论/规则)           │
│    └────────────┬─────────────┬────────────┘                   │
│                 ▼             ▼                                 │
│         analysis(上下文组装 + 建议校验) ◄── AI 在引擎之外         │
│                 ▼                                              │
│  proposal ──► approval ──► action(模拟执行) ──► observation      │
│                 ▼                                              │
│           evaluation(验收) ──► experience(经验库)               │
└──────────────────────────┬────────────────────────────────────┘
                           │
┌──────────────────────────▼────────────────────────────────────┐
│  本地数据与知识层                                               │
│  SQLite（WAL 模式，结构化业务数据 + 审计）                       │
│  data/raw/（原始报表，只增不删，gitignore）                      │
│  methodology/（方法论版本 YAML，入 git，人工审核后生效）          │
└───────────────────────────────────────────────────────────────┘
                           ▲
┌──────────────────────────┴────────────────────────────────────┐
│  外部数据来源层（与核心解耦，PRD 3.1 要求）                      │
│  手动上传报表 / Agent 代取（领星 MCP、西邮洞察、SoftTime）/      │
│  亚马逊官方 API（后续）—— 均经由 ingest 统一入口进入             │
└───────────────────────────────────────────────────────────────┘
```

**关键点：AI 位于引擎之外。** 核心引擎不调用任何 LLM。引擎只做两件事：
1. `assemble_analysis_context()` —— 把事实、档案、事件、方法论、相关经验打包成"分析上下文包"（JSON）交给 Harness 侧的 AI；
2. `validate_proposal()` —— 对 AI 返回的结构化建议做 JSON Schema 校验 + 硬规则校验 + 证据引用存在性校验，通过才允许进入提案表。

这是 PRD「原则二：事实与判断分离」的物理边界，也让 T1/T2/T3/T6/T8 可以在完全不调用 LLM 的情况下测试。

### 1.2 核心设计决策（D1–D10）

| # | 决策 | 内容与理由 |
|---|---|---|
| D1 | **接口形态：CLI 先行** | service 层 + typer CLI 是第一入口；Harness 插件只是薄适配（若 Harness 能执行本地命令则直接调 CLI 的 `--json` 输出；若仅支持 MCP，则用 fastmcp 包 service 层，MCP 提前到阶段一，成本约 1–2 天，可接受）。**核心引擎的实现不依赖这个答案** |
| D2 | **存储访问：SQLAlchemy 2.0 + Alembic** | 18 个对象 + 版本化 + 大量外键引用（提案→方法论版本→档案版本→数据批次），手写 SQL 迁移易错；Alembic 提供可追溯 schema 版本。SQLite 开 WAL 模式。备选：若想零依赖可用 stdlib sqlite3 + 手写迁移，但 18 表规模下维护成本更高，不推荐 |
| D3 | **AI 在引擎外**（见 1.1） | 事实与判断分离；引擎可确定性测试；换模型零成本（对应 PRD 2.1"更换 Agent 不应重新开发"） |
| D4 | **建议校验器（proposal validator）** | AI 输出必须过三关：JSON Schema（14 必填字段）→ 硬规则（数据成熟度/权限/调整幅度边界/冷却期）→ 证据存在性（建议中引用的每条 fact_id / event_id / rule_id 必须在库中存在）。任一关失败，建议标记为 `rejected_by_validator` 并记录原因，不进入审批 |
| D5 | **版本化采用 SCD-2 式版本表** | `methodology_versions`、`product_profile_versions` 均为"版本行"表（不物理覆盖旧行）；`analysis_runs` 记录 `{methodology_version_id, profile_version_id, data_batch_ids[]}` 快照引用，满足"历史分析可还原当时背景"（PRD 4.2/4.6） |
| D6 | **导入幂等** | `raw_datasets.file_hash` 唯一约束；重复上传返回既有批次号并提示；同一报表不同版本共存（状态区分），满足 T1"不静默覆盖"。动作侧以 `action_id` 为幂等键 |
| D7 | **经验检索：SQLite FTS5** | 中文按字符二元切分（无需分词器依赖）建全文索引；经验库量级（先几十条、长期数百条）远未到需要向量库的程度，符合 PRD 8.3"暂不实现向量数据库" |
| D8 | **审计：append-only** | `audit_log` 表 + SQLite 触发器禁止 UPDATE/DELETE；审批、导入、校验拒绝、状态变更全部落审计。满足 PRD 7.3 |
| D9 | **配置与密钥分离** | `.env`（gitignore）+ 环境变量；`methodology/*.yaml`、`profiles/*.yaml` 入 git（业务知识应版本化）；`data/` 整目录 gitignore。密钥不进入分析上下文包（PRD 7.3"密钥不得暴露给分析模型"——由 D3 的上下文组装白名单保证） |
| D10 | **时间与币种口径** | 报表日期按站点时区原样存储 + 统一记录 marketplace/currency 字段；T-2 窗口、成熟度天数等全部来自方法论参数而非硬编码。满足 T2 口径测试 |
| D11 | **多数据口径统一层（canonical staging）**——用户 Q3 备注，2026-11-14 新增 | 数据管道固定为三段：`源报表 → 源适配器 → canonical 统一中间层 → 事实层`。① 每个数据来源（亚马逊 bulk、领星、西邮洞察、官方 API…）一个**源适配器**，负责该源的列名映射与口径标注（source、口径版本、币种、时区、统计口径）；② canonical 层是唯一汇合点：字段名/维度/度量统一、跨源去重、冲突显式标记（不静默取舍）、每行保留 `source_lineage`；③ **事实层只允许从 canonical 层构建，禁止直接读源报表**——未来新增口径只写适配器，事实计算与下游零改动。落地对象：`NormalizedDataset`（PRD 第六章）按此扩展为 canonical 模型，源适配器产出 `RawDataset` 的解析视图 |

### 1.3 建议目录结构

```
AD system/
├─ ads_core/                  # 核心业务引擎（无 LLM 依赖）
│  ├─ ingest/                 # 报表识别（列名指纹）、导入、幂等
│  ├─ normalize/              # 清洗、标准化、口径统一
│  ├─ quality/                # 数据质量检查、状态判定
│  ├─ facts/                  # 指标计算（可复算）
│  ├─ profile/                # 产品档案 + 版本
│  ├─ events/                 # 业务事件
│  ├─ methodology/            # 方法论加载、三层规则、版本
│  ├─ analysis/               # 上下文组装 + 建议校验器
│  ├─ decision/               # 提案/审批/动作(模拟执行)/回执
│  ├─ observation/            # 观察窗口状态机 + 效果验收
│  ├─ experience/             # 经验库 + FTS5 检索
│  ├─ storage/                # ORM 模型、迁移、DAO、审计
│  └─ cli.py                  # typer 入口（--json 输出）
├─ ads_harness/               # DeepSeek Harness 插件适配（阶段一末）
├─ ads_mcp/                   # MCP Server（阶段五）
├─ data/                      # gitignore：raw/、ads.db
├─ methodology/               # 方法论版本 YAML（入 git）
├─ profiles/                  # 产品档案初始 YAML（入 git）
├─ docs/                      # 需求基线、架构评审、各阶段交付文档
└─ tests/                     # pytest：T1–T8 映射（见 §4）
```

### 1.4 数据对象落地补充

PRD 第六章 18 个对象全部保留，另建议补充 4 个系统对象（不改变业务语义）：

| 补充对象 | 用途 |
|---|---|
| `ImportBatch` | 导入批次（PRD 4.1 已隐含要求"导入批次"字段，独立成表便于追溯） |
| `AuditLog` | 审计流水（PRD 7.3 明确要求，需独立对象） |
| `MethodologyRule` | 方法论内的单条规则行（三层规则的归属、参数、状态），`Methodology` 表头管版本元数据 |
| `Evidence` | 建议引用证据的规范化存储（fact/event/rule/experience 的多态引用），支撑 D4 校验与 T5 追溯 |

### 1.5 业务流程 → 模块映射

PRD 5.1 十七步流程中，第 1 步（取数）在接入层，第 10 步（AI 分析）在 Harness 侧；**其余 15 步全部由引擎内确定性代码完成**。流程中"任何环节出现关键数据缺失/规则冲突/权限不足必须暂停"实现为：每个环节输出带状态的 `gate` 结果，任一 gate 失败则流程停在当前态并记录，不得跳过（对应 PRD 5.1 末段）。

## 2. 需求可行性逐项评估

| PRD 模块 | 可行性 | 评估 |
|---|---|---|
| 4.1 数据接入与管理 | ✅ 高 | 报表识别用"列名指纹匹配"（中英文列名映射表），不依赖文件名；幂等/批次/哈希均有标准做法。**依赖：真实报表样本校准列名映射** |
| 4.2 产品档案管理 | ✅ 高 | 档案结构（A–F 六组）适合 YAML 定义 + 版本表存储；初始录入建议用 YAML 文件 + CLI 校验导入（见 Q4） |
| 4.3 业务事件管理 | ✅ 高 | 简单 CRUD + 分析窗口相交查询；纯程序逻辑 |
| 4.4 历史数据与快照 | ✅ 高 | 快照即按日聚合的指标行；对比查询为标准 SQL；"修正建新版本"与 D5 同模式 |
| 4.5 指标与事实计算 | ✅ 高 | 公式固定可复算；"不可计算明确标记"落地为 `computable=false + reason` 字段，天然满足 T2 |
| 4.6 方法论与规则管理 | ✅ 中 | 三层规则分层清晰可落地；**风险在输入而非实现**：完整方法论目前在 Notion，需专项结构化为 YAML v1（见 R2）。PRD 已给的 4 条（SP≥7 天、SB/SD≥14 天、T-2、样本不足继续观察）可直接作为硬规则/参数样例 |
| 4.7 AI 广告分析与决策 | ✅ 中 | 七步流程 = 引擎按序组装上下文包；建议 14 字段 = Schema 约束。判断质量本身不可程序化保证，靠 D4 校验 + 阶段四人工核对兜底（PRD 阶段四本身就这么设计的，自洽） |
| 4.8 建议与审批 | ✅ 高 | 结构化提案 + 状态机（待审/批准/拒绝/修改后批准/暂缓）；"修改后批准保留最终版"即审批记录关联修订快照 |
| 4.9 动作管理与执行核验 | ✅ 高（阶段一）/ ⚠️ 后续 | 阶段一仅模拟执行（dry-run 记录），简单；后续接入亚马逊 API 的幂等/回执/回读/回滚是标准工程问题，架构已预留（动作状态机 + ExecutionReceipt 表） |
| 4.10 观察窗口与验收 | ✅ 中 | 四种裁决状态机可实现；"证据不足"裁决路径明确。**注意 T-2 滞后**：观察期结束但数据未到位时，自动裁决为"证据不足"并保留重开能力（见 R5） |
| 4.11 经验沉淀 | ✅ 高 | 结构化经验表 + FTS5；经验只增不删（失败经验保留 = 状态标记而非物理删除） |
| 权限（第七章） | ✅ 高 | 单用户本地系统，第一阶段"只读"本质是**流程约束而非技术 ACL**：AI 的写入口只有 create_proposal / create_observation_task / propose_rule_change 三个，其余写操作仅 CLI 人工触发——用接口面控制即可实现，无需引入权限框架 |
| 安全（7.3） | ✅ 高 | .env + gitignore + 审计触发器 + 上下文包白名单，均为常规做法 |

## 4. 测试策略映射（T1–T8 → 实现方式）

| 测试 | 自动化程度 | 实现方式 |
|---|---|---|
| T1 数据污染 | **全自动** | pytest：构造重复/缺列/币种冲突/多版本样本，断言批次状态与不覆盖行为 |
| T2 指标口径 | **全自动** | 混合广告类型/窗口样本，断言拒绝混合计算、可复算、不可计算标记 |
| T3 数据成熟度 | **全自动** | 未成熟样本 → 断言只进观察态、不产生执行级建议（D4 校验器拒绝） |
| T4 产品背景 | 半自动 | 固定样本（秒杀/调价/断货/排名变化场景）→ 结构断言 + 人工复核清单 |
| T5 决策依据 | **全自动（结构）** + 人工（内容） | 断言每条建议 14 字段齐全、证据 ID 存在、版本可追溯 |
| T6 权限 | **全自动** | 无审批不执行、审批≠执行授权、超范围拒绝（接口面 + 状态机断言） |
| T7 动作归因 | 半自动 | 结构断言（同期事件清单出现在分析上下文与建议中）+ 人工复核 |
| T8 观察与回滚 | **全自动** | 幂等（重复触发不重复建动作）、状态查询、回滚条件触发、历史完整 |

> 结论：8 项中 5 项可全自动化，3 项半自动化且人工部分与 PRD 阶段四设计天然重合，**测试要求整体可满足**。
